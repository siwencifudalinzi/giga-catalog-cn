# GIGA 无详情影片与子表故障隔离设计

日期：2026-09-17
状态：待用户审阅；尚未实施

## 1. 目标与边界

将已成功读取的影片链接表格中，暂时不能可靠对应正式影片的记录，公开展示在独立的「无详情影片」入口。每条在页面上只显示编号和一个或多个外部链接；不猜测正确番号，不生成标题、封面、发布日期、标签或站内播放器。正式目录的 `catalog.json`、影片总数、每日官网同步和链接更新日志继续各司其职。

本功能覆盖主链接表、可用的系列子表和可选的历史影片表；字幕专用表不产生「影片链接」记录。来源网页整体不可用时没有可解析的新行，必须与“有行但未匹配”分开处理。当前定点修复提交 `b3c3d12414354cb7aae579e950d0621f70af1483` 只是恢复同步：GHVR 子表 404 被隔离，PMID 表的 8 个已核实错号被跳过。通用功能上线并通过验证后，移除这两处临时特例。

## 2. 方案选择

采用独立公开数据文件和按需加载的页面入口：未知行不伪装成官网影片，首屏也不增加下载负担。拒绝把占位影片插入 `catalog.json`，因为这会污染正式数量、排序、标签及运行时分片；也拒绝只写后台诊断，因为用户需要在手机上查看和打开链接。无需为此引入账号或私有后端：该区域与现有目录一样公开，链接本身也会出现在公开数据文件中。

## 3. 行级判定

每个来源先沿用自己的表格结构校验，再对无详情候选链接额外要求公开 HTTPS、无凭据、无内网/本地目标；系列子表还必须满足现有 `ouo.io` 短链格式。格式合规不等于已经验证链接仍可访问。可用的影片链接行划分为：

1. **正式匹配**：规范化后的编号在正式目录存在，且来源系列关系可信；按现有逻辑更新正式影片链接。
2. **无详情**：编号可按现有 `normalize_code` 规则规范化，链接通过来源对应的安全校验，但编号在正式目录不存在。既包括同系列未收录番号，也包括 PMID 表中 `PIMD-105`、`PMIF-109` 这类错系列前缀。只规范大小写和数字格式，绝不把 `PIMD` 猜改成 `PMID`。
3. **无可用链接**：空单元格或 `NEED ASK FOR REUP` 不生成无详情项，保留现有待补链语义。
4. **不可安全归类**：缺少可识别编号、危险 URL、已在正式目录存在却与来源系列冲突、或整表结构错误，不进入无详情项；记录明确诊断。危险 URL 和可信来源关系冲突仍阻止发布，而不是绕过原校验。

同一未知编号、同一 URL 去重；同一未知编号的多个**各自通过校验**的 URL 全部保留，按稳定顺序展示，不擅自选一个“正确链接”。正式影片的同槽位冲突处理保持原规则。短链、Streamtape 观看页和其他 HTML 落地页只可外部打开，不解析、不代理、不用作 `<video src>` 或 iframe。

## 4. 来源暂时不可用

主链接表、目录表或官网抓取的失败仍按现有发布闸门处理，不用子表容错掩盖。独立的影片子表遇到 404、408、429、5xx、连接错误或超时，可在**来源身份未改变**且单次失败不超过 3 张活动子表时隔离该来源：

- 已有上次成功快照：保留这张表上次确认的未知项；正式影片既有链接仍由现有追加保留机制保留。其他可用子表继续同步。
- 从未成功读取：本轮不为它制造编号或链接，只报告该子表不可用。
- 子表 URL/系列身份改变后不可用、超过 3 张活动子表不可用、返回可疑 HTML/不符合结构的 CSV，或认证/权限错误：阻止整次发布，等待核查。

可选历史表原有的非关键来源隔离不被收紧；无论哪类隔离，都要在私有同步摘要和公开的无 URL 更新状态中明确标记“部分来源未更新”，不能显示成全量成功。GHVR 目前的 404 不会凭空生成无详情影片。

## 5. 数据与更新流程

- `public/data/unmatched-links.json`：公开、确定性排序、独立于正式目录的版本化文件。每项仅含规范化编号 `code` 与非空、安全、去重的 `links` 字符串数组；顶层仅含 `schemaVersion`、`generatedAt` 和 `entries`。页面不显示额外来源字段。文件由前端在进入该视图时懒加载，不预加载。
- `data/state/unmatched-link-sources.json`：按来源系列与精确源 URL 保存上次成功读取的未知行及时间，用于单表故障时保留旧数据。该文件不进入 `public/`；虽不由网站提供，仓库仍是公开仓库，因此不得写入凭据、Cookie、私有 URL 或令牌。
- 每轮成功读取某个来源后，以该来源新快照替换其旧快照；该来源删除的行才可从公开无详情列表移除。来源读取失败时不删除其旧快照。所有来源汇总后按编号与 URL 去重。
- 一个无详情编号后来与正式目录**精确匹配且来源关系可信**时，在同一次发布中从无详情列表移除并交给正式目录；不做模糊合并。未知列表变化即使正式 `catalog.json` 不变，也应触发发布。
- 一次 `refresh.py` 产生的正式目录、无详情文件、来源快照和摘要必须在验证后原子发布；任一写入失败回滚到上一版。后续标签同步只改变正式目录的标签和运行时分片，不改变影片编号集合或无详情文件；release manifest 对标签同步后的最终公开文件逐个校验。GitHub Actions 显式暂存新增文件。

若单次新增无详情编号超过 100 个，先阻止发布并输出数量与来源摘要，避免官网抓取或表格结构故障被误解释成大量“未知影片”。这只约束新增异常，不限制已经核实并持续存在的旧项。

## 6. 页面行为与安全

在现有目录导航加入「无详情影片」，桌面和手机均可进入；进入后显示按编号排序的简洁列表和编号搜索。每条只出现编号和链接操作，空列表有清晰提示。链接使用现有安全外链组件或等效验证，`target="_blank"` 时必须设置 `rel="noopener noreferrer"`；不将 URL 放入页面地址、`data-*`、错误文案或日志。加载失败只影响本视图，正式目录仍能浏览并提供重试。保持键盘可达、可见焦点、44px 触控目标，以及 320px、390px、768px、1440px 和 200% 缩放下无横向溢出。

## 7. 验证与发布

先以真实源的只读采样建立基线，再用测试覆盖：PMID 8 条错号与正常行共存、同系列未收录号、重复/多链接、恶意 URL、空链接、来源身份变化、单表 404 与恢复、超过故障上限、异常数量闸门、首次无快照、正式匹配后的迁移、原子回滚和 `catalog.json` 数量不变。前端测试覆盖懒加载、搜索、纯外链、安全转义和错误重试；真实浏览器检查手机与桌面布局。发布前运行完整 Python/Node 测试、`git diff --check`、生成文件/manifest 校验；部署后验证 GitHub Pages 上正式目录和无详情文件均与该次最终提交一致。若失败，保留上一版公开数据并回滚本功能提交，不删除已有正式影片链接。
